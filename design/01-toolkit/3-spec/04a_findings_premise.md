# 04a. 전제의 교체: 검증 엔진에서 구성 계층으로

> 사이 문서. 04 검증 엔진 안 → 05 구성 계층 스펙으로 넘어가면서 바뀐 전제와, 그 전제 아래에서 새로 정리된 로거 요구사항.

## 스택 구성의 근거를 되짚음

"이 스택은 무엇을 근거로 했나"라는 질문에 답하면서 근거의 강도를 나눴다.

| 근거 | 내용 | 강도 |
|---|---|---|
| README 수준 조사 | 17개 프로젝트의 README와 구조. 코드 실행이나 산출물 비교는 없음 | 약함 |
| stop-slop-ko 벤치마크 | 유일한 정량 근거. 규칙 준수 100 vs 94.2, 블라인드 품질 5:5 | 중간. 자기참조 채점 |
| fluent-korean 관리자 운용 방식 | output-style → 재적용 → 적대적 검증 | 중간. 한 사람의 경험 |
| 구조적 추론 | 생성 시점/후처리 구분, taxonomy 동시 로드 시 priming 희석 | 타당하나 미측정 |
| 사용자의 기존 관심사 | artifact + provenance + verification | **설계 비중을 결정한 주된 근거** |

L3 gate, L4 eval, sidecar report, `pass: null` 규칙, category_map, vendoring lock 같은 무거운 장치는 upstream이 못 미더워서가 아니라 **사용자가 검증을 우선한다고 알고 있었기 때문에** 들어갔다. upstream 신뢰도에 대한 증거는 긍정도 부정도 없었다. 재지 않았다.

## 바뀐 전제

> upstream이 굉장히 신뢰할 만하다는 가정 하에서 사용성을 우선한다.

이건 설계의 오류를 고치는 게 아니라 전제를 사용자 의도에 맞게 바로잡는 것이다. 04 문서는 폐기가 아니라 보류로 남긴다.

전제의 두 층위를 구분해둔다. **동작한다**(설치되고 하라는 대로 한다)는 믿어도 된다. **효과가 있다**(넣으면 좋아진다)는 유일한 데이터가 stop-slop-ko의 5:5이고, 이건 잘 프롬프트된 모델 위에서는 차이가 작다는 쪽이다. 가정이 약한 지점은 후자다.

## 무엇이 달라지는가

검증 엔진은 LLM 층을 신뢰하지 않고 report만 보증했다. 구성 계층은 이미 있는 upstream들을 프로파일과 프리셋으로 묶어 에이전트에게 붙여주는 얇은 층이다.

| 항목 | 검증 엔진 (04) | 구성 계층 (05) |
|---|---|---|
| upstream 취급 | vendor 복사, lock, 수정 금지 | 각자의 설치 경로. 버전은 마켓플레이스가 관리 |
| rewrite / diagnose | im-not-ai와 yoonmoon 분리, category_map | im-not-ai 자체 진단→윤문 흐름 그대로. yoonmoon은 detect만 원할 때 |
| gate | 5개 capability 조합, fail-closed | 없음. im-not-ai의 변경률·보존 invariant를 신뢰 |
| report | 5필드 스키마, executed_by, pass:null | upstream 출력(변경률 %, 등급) 그대로 통과 |
| eval | 단계 승격의 관문, stage 0 필수 | 없음 |
| policy | 블록 합성 + 해시 | fluent-korean 플러그인 + README 블록 몇 줄 |
| MCP 서버 | 필수 | 초기에는 불필요. SKILL.md + 에이전트 템플릿 |
| baseline 코퍼스 | 필요 | 불필요 |
| 사용자 재료 | 글 샘플, 세션 로그 | 없음 |

## 무엇이 달라지지 않는가

신뢰 문제가 아니라 구조 문제였던 것들은 남는다.

- 생성 시점 / 후처리 구분
- rewrite taxonomy 하나만 (priming 희석 때문이지 불신 때문이 아님)
- 서브에이전트에 정책 전파 (fluent-korean 자체가 권함)
- 두 방향(주입, 위임)과 단계 선택 — 사용자가 정의한 재사용성이라 오히려 더 중요해짐

## 되돌아갈 길: 부분집합 원칙

> 이 절에서 항목을 가른 기준("검증이냐 아니냐")은 나중에 한 번 교정된다. 갈랐어야 할 선은 **판정하느냐 측정하느냐**였고, 그 차이 때문에 `ko.features`와 버전 고정이 04에 잘못 남았다(→ `05a_findings_measurement.md`).

구성 계층은 검증 엔진의 부분집합으로 설계한다. 프로파일·프리셋·에이전트 템플릿은 두 버전이 같은 형식을 쓰고, 검증 엔진의 gate·report·eval은 나중에 **더하는** 것이지 구조를 바꾸는 게 아니다. "upstream을 믿었는데 어느 지점에서 안 믿게 됐다"가 생기면 그 지점에만 gate를 끼운다.

## 로거: 유일하게 남기는 검증 장치

gate가 아니라 **로거**를 남긴다. policy를 켜고 끈 산출물과 토큰 수를 쌓아두되 판정하지도 차단하지도 않는다. 나중에 효과가 궁금해질 때 그때 재료를 모으면 늦기 때문이다.

로거가 "나중에 바로 검증에 쓰이는" 조건 두 가지:

1. **eval 케이스 형식으로 기록한다.** 그냥 로그를 쌓으면 변환 시점에 컨텍스트가 없어 변환이 안 된다.
2. **간헐적으로 policy를 끄고 돌린다.** 자연스럽게 쌓이는 건 전부 on 샘플이라 대조군이 없다.

## 로깅 데이터의 축

"한국어를 위한 것"이라는 조건은 하나가 아니다. 지시를 한국어로 하는 것, 작업 대상이 한국어인 것, 사고를 한국어로 하는 것은 **서로 독립인 조건**이고 한 실행에서 세 값이 다 다를 수 있다. policy의 효과는 조합마다 다를 가능성이 높다.

| 축 | 값 | 관측 방식 |
|---|---|---|
| 지시 언어 | ko / en / mixed | 프롬프트에서 직접 |
| 산출물 언어 | ko / en / mixed | 산출물에서 직접. mixed면 한국어 span만 추출 |
| 사고 언어 | instructed / not | **지시 여부만.** thinking이 보이면 언어 비율 추가 |
| 컨텍스트 영어 비율 | 0~1 | 시스템 프롬프트·도구 출력·코드의 영어 비중. priming 부하 |
| 하네스 위치 | main→user / sub→orchestrator / sub→sub | 누적 문제가 생기는 지점 |
| 세션 상태 | 턴 수, 누적 토큰 | 효과 감쇠 |
| 주입 지점 | output-style / CLAUDE.md / system 문자열 / none | policy_on의 세부 |
| 모델 | 이름+버전 | |
| 작업 유형 | coding / writing / analysis | 코딩 지침과의 경합 |

사고 언어를 "관측"이 아니라 "지시"로 적는 이유: 통제도 관측도 안 된다. `think-in-korean` 블록의 유일한 실험은 켜고 껐을 때 **작업 성공률**이 달라지는지이고, 한국어 품질 수치로는 답이 안 나온다.

## 로깅 대상의 조건

- **모델이 생성한 한국어만.** 사용자 입력의 반복, 도구 출력 붙여넣기, 인용은 제외. 안 가르면 fluent-korean의 효과를 사용자의 글로 재게 된다.
- **최소 분량.** 한국어 어절 N개 미만은 버린다.
- **재시도 중복 제거.**
- **대조군 짝.** off 샘플은 같은 작업 유형·하네스 위치·주입 지점의 on 샘플과 짝이 있어야 한다. 그래서 off 규칙은 무작위가 아니라 **층별로** 돈다.
- **축이 빠진 샘플은 A/B에서 제외.**

A/B는 전체 평균이 아니라 층 안에서만 유효하다. "policy가 효과 있었나"는 답이 없고 "지시 ko · 산출물 ko · sub→orchestrator · 긴 세션에서 효과 있었나"만 답이 있다.

## 로거의 토큰 비용

거의 0이다. 토큰은 LLM이 일할 때만 나가고 로거는 하네스 밖의 스크립트다. 산출물 캡처는 Claude Code라면 Stop hook에 넘어오는 transcript 경로에서, Codex는 세션 파일에서, 직접 만든 하네스면 API wrapper에서 한다. 축은 전부 텍스트·설정·메타데이터에서 계산된다.

토큰이 새는 지점 셋과 회피:

| 지점 | 회피 |
|---|---|
| 에이전트 자기 보고 (policy_hash echo 등) | 하네스가 주입 지점·위치를 기록하면 불필요. lite에서는 안 넣음 |
| 작업 유형을 LLM으로 분류 | 규칙(사용된 도구가 Edit/Write면 coding)으로 하거나 비워둠 |
| on/off 짝을 같은 작업에 두 번 | 층별 교대. off 실행은 fluent-korean이 늘리는 만큼 오히려 덜 씀 |

주의: 로그 파일을 작업 디렉터리 안에 두면 에이전트가 읽어 컨텍스트를 채운다. 작업 트리 밖에 둔다.

토큰을 쓰는 건 로거가 아니라 fluent-korean 자체이고, 로거는 그게 얼마나 쓰는지 알려주는 쪽이다.
