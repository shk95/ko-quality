# 01. 아이디어: 넣은 것이 효과가 있는지 아는 법

> 단계 문서. 이 시점에는 문제 의식과 바라는 방향만 있고, 요구의 정의는 아직 느슨하다.
> 입력은 `../../01-toolkit/7-review/review.md` §G다.

## 출발점

시대 01은 "설치하면 쓰이는 도구"를 지었고 그것으로 끝냈다. Claude Code에서는 정책이 메인 대화와 서브에이전트 양쪽에 걸리고, 스킬 넷이 불리고, hook 로거가 레코드를 쌓는다. 검증은 처음부터 다음 단계로 미뤄 둔 것이었다(06 §1).

미뤄 둔 질문은 그대로 남아 있다. **넣으면 좋아지는가.**

04a가 전제를 두 층위로 나눌 때 이미 적어 두었다 — upstream이 **동작한다**(설치되고 하라는 대로 한다)는 믿어도 되지만, **효과가 있다**(넣으면 좋아진다)는 근거는 stop-slop-ko의 블라인드 5:5 하나뿐이고, 그것은 잘 프롬프트된 모델 위에서는 차이가 작다는 쪽이다. 시대 01은 이 약한 지점을 건드리지 않고 재료만 남겼다.

지금 있는 재료:

- `~/.ko-quality/logs/<profile>/<yyyy-mm>.jsonl` — 프로파일, 하네스, 위치(main-to-user / sub-to-orchestrator), 프롬프트 원문, 산출물 원문, upstream 커밋 넷, `usable`
- 고정된 upstream 네 종과 조각마다 붙은 출처(앵커 + 해시)
- 같은 정책 본문이 네 산출물에 문자열로 동일하다는 것을 매 빌드가 강제하는 검사 넷

없는 것: 대조군, `features`, `outcome`, threshold, eval. 06 §15가 "더하는 것"으로 열거한 그대로다.

## 리뷰가 바꾼 전제

7-review에서 사용자 요청으로 `claude plugin eval`의 정책 케이스를 runs 3으로 다시 돌렸다(C3). 결과가 검증 단계의 출발점을 바꾼다.

| 프로파일 | LLM 판정기 통과 (플러그인 켬 / 끔) | 기계적 지표 (켬 / 끔) |
|---|---|---|
| agent-reply | 0/3 / 0/3 | 줄표 0/3 / 2/3 |
| formal-report | 2/3 / 1/3 | 사용자님 2/3 / 0/3 |

판정기는 줄표가 없고 합니다체로 끝나는 agent-reply 응답 셋을 전부 실패로 매겼고 이유를 말하지 않았다. 반대로 자기 루브릭이 FAIL이라고 규정한 기준선 응답(사용자님을 한 번도 쓰지 않은) 하나를 통과시켰다. 같은 응답에서 기계적 지표는 정책 효과를 그대로 보여줬다.

**그래서 검증 단계의 첫 과제는 gate를 만드는 것이 아니라 판정기를 믿을 수 있는지 먼저 재는 것이다.** 05a는 판정과 측정 사이에 선을 그었는데, 그 위에 한 겹이 더 필요하다 — 재는 도구 자체의 검증. 이것을 건너뛰면 `watch:`에 쌓이는 값이 무엇을 재는지 모르는 채로 threshold가 붙는다.

## 원하는 것

06 §15의 목록이 골자이고, 순서는 위 전제 때문에 바뀐다.

1. **측정을 먼저.** `features` 계산(판정 없이 값만), 레코드에 `outcome`, 그리고 정책을 끄는 대조군. 무엇을 재는지가 먼저 고정돼야 한다.
2. **판정기를 검증.** 기계적으로 잴 수 있는 규칙은 기계적 채점기로 내린다. LLM 채점기는 쓰기 전에 사람 판정 또는 기계 판정과의 일치도를 측정한다. 일치도가 낮으면 쓰지 않는다.
3. **표시에서 판정으로.** `watch:`(넘어도 막지 않고 레코드에 표시)를 먼저 돌리고, 값이 쌓여 의미가 생긴 항목만 `gate:`로 승격한다. 05a가 정한 대로 키 이름만 바꾸는 승격이다.
4. **eval.** 규칙을 더하거나 고치기 전에 통과해야 하는 관문. 케이스 형식은 04 §13.1에 초안이 있다.

산출물이 "계측 장치"가 되는 것은 이 시대에서는 허용된다. 시대 01이 도구를 앞에 세운 이유(사용성 우선)는 이미 달성됐다.

## 범위 밖

- **Codex 채널 재시험.** 시대 01이 받아들인 release-blocked 3건과 재판단 대상 2건은 전부 Codex 쪽이다. 미뤄 둔 이 실측이 검증 장치 설계를 붙잡지 않도록 임시 시대 `99-codex-retest`로 분리한다. 02는 Claude Code 레코드만으로 진행할 수 있다.
- **정규화 포맷 재설계(C2).** 검증 단계가 `normalized/`를 읽어야 할 때 다시 본다. 읽을 일이 없으면 그대로 둔다.
- **새 upstream 도입.** `ruleset` 공급자를 고르는 일은 이 시대 안에 있지만, 정책 조각 공급자를 늘리는 일(stop-slop-ko)은 아래 열린 질문으로 남긴다.

### 근사치 재검토 목록 (06 §13.1)

06 §13.1은 스펙의 일부이고, 거기 적힌 아홉 항목은 값이 나오되 정확하지 않다. 같은 절이 **threshold를 걸기 전에 각각을 다시 보라**고 못박았는데, threshold를 실제로 거는 시대가 02다. 7-review의 §B(스펙 개정 후보)와 §G(인계)는 이 목록을 열거하지 않았으므로 여기서 직접 받는다. `task_type`만 §G의 열린 발견으로 이미 들어와 있고, 나머지 여덟은 이 표가 유일한 인계 경로다.

| 항목 | 06이 남긴 처리 방침 | 02가 다시 볼 것 |
|---|---|---|
| `context_en_ratio` | 06에서 레코드에서 뺐다 (시스템 프롬프트가 hook 입력에 안 보임) | 되살린다면 "도구 출력 기준 영어 비율"로 이름과 정의를 바꾼 뒤에만. 옛 이름으로 부활시키지 않는다 |
| `task_type` | 도구 호출 규칙 근사. `task_type_method: rule`을 함께 남기고 LLM 분류로 도망가지 않는다 | `Write`로 한 글쓰기를 못 가리는 것(§G 열린 발견)까지 같은 항목이다. 규칙을 고치든 값을 버리든 한 번에 정한다 |
| `instruction_lang` | 정의를 "직전 사용자 입력의 한글 비율"로 좁혀 적는다 | 좁힌 정의가 레코드와 features 양쪽에 같은 뜻으로 적혀 있는지 |
| `artifact_lang`의 mixed | 주석·문자열·마크다운 문단만 추출, 실패 시 `usable: false` | 코드 + 한국어 주석 산출물에서 실제 오염률. 채점기가 이 값을 쓰기 전에 |
| `output`의 순도 | 인용·코드 블록 제거 후 한국어 어절 20 미만이면 버린다 | 남은 텍스트에 사용자 입력 인용이 섞이는 비율. 기계적 채점기의 입력이 되는 값이다 |
| `tokens.output` | 문자 수 추정 + `method: estimate`. 서브에이전트는 `Agent` 도구 `PostToolUse`의 `usage` | 추정과 실제의 차이를 한 번 재고, threshold에 쓸 값인지 정한다 |
| `sub-to-sub` | P7 결정 2에서 **미방출**로 확정 (hook 입력에 부모가 없음) | 판별 방법이 새로 생겼는지 확인하고, 없으면 값 자체를 스펙에서 뺀다 |
| 변경률 | 모델 자기 보고. 원문 그대로 `upstream_report`에 두고 별도 필드로 올리지 않는다 | 코드 판정 `ko.change_rate`(§15)를 이 시대가 만든다. 자기 보고와 계산값을 같은 필드에 섞지 않는다 |
| Codex `instructions`의 정책 요약 | P6 결정 2에서 채널을 **없음**으로 닫아 `adapted` 행이 사라졌다 | 99의 재시험이 채널을 되살리면 이 행도 되살아난다. 그때만 본다 |

`sub-to-sub`와 Codex `instructions` 둘은 Claude Code 레코드만으로는 결론이 나지 않는다. `99-codex-retest`의 결과를 합치는 지점이 여기다.

## 초기 가설

- **기계적으로 잴 수 있는 것이 생각보다 많다.** 줄표, 호칭, 문장 종결 형태, 조사·어미 탈락, 명사 나열 밀도는 규칙으로 센다. C3가 보여준 것도 그쪽이다.
- **층이 곱해져 표본이 모자란다.** 05a의 계산대로 profile 2 × position 3 × injection 4 × task 3 = 최대 72층이고, 층당 대조 표본이 쌓이려면 수천 세션이 든다. 효과가 작을수록 표본이 커야 한다.
- **그래서 층을 줄이는 것이 설계다.** 무엇을 고정하고 무엇을 교대시킬지가 이 시대의 실제 결정일 가능성이 크다.
- **LLM 판정은 보조로만 남는다.** 사람이 읽어야만 알 수 있는 항목(자연스러움, 유용함)이 남겠지만, 그것에 threshold를 걸지는 않는다.
- **로거는 계속 판정하지 않는다.** 측정이 판정으로 새는 문(05a)이 이 시대에 실제로 열린다. 그 문을 어디에 두는지가 중요해진다.

## 이 단계에서 열린 질문

- **무엇을 "좋아졌다"로 볼 것인가.** 규칙 준수율인가, 산출물의 유용성인가, 다중 에이전트 경로에서의 의미 손실인가. 셋은 다른 측정이다.
- **대조군을 실제로 돌릴 수 있는가.** k번째 세션마다 정책을 끄는 것은 사용자가 쓰는 도구의 품질을 일부러 떨어뜨리는 일이다. 허용 범위와 고지 방식을 정해야 한다.
- **판정기를 얼마나 재야 쓰는가.** 일치도 몇 퍼센트, 표본 몇 건이 기준인가. C3는 케이스 3건으로 판정기를 기각했는데, 그 판단 자체의 표본도 작다.
- **gate가 걸리면 무엇을 하는가.** 막는가, 다시 시키는가, 표시만 하는가. 04의 `on_final_fail`이 초안을 갖고 있다.
- **로그로 평가를 돌려도 되는가.** 레코드에는 프롬프트와 산출물 원문이 들어간다. 마스킹은 하지만 개인 텍스트다. 평가에 쓰는 범위와 보관 기간을 정해야 한다.
- **stop-slop-ko를 넣을 것인가.** 검증 장치가 생기면 "넣어 보고 재면" 되는 문제로 바뀐다. 그때 `exempt`도 함께 복구한다.
- **Codex 결과가 늦게 도착한다.** 99가 끝나기 전에 02가 진행되므로, Codex 쪽 측정이 빠진 채로 설계된 장치가 나중에 Codex에서도 서는지 어떻게 보장할지.
