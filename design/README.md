# ko-quality 설계 기록

`ko-quality` 프로젝트의 설계 문서와, 그 설계를 지으면서 내린 판단과 실제로 지어보니 달라진 것을 함께 두는 디렉터리입니다. 구현 코드는 저장소 루트에 있고, 이 디렉터리는 **왜 그렇게 지었는가**만 담습니다.

## 지금 할 일

**현재 위치:** `06` 툴킷 스펙의 프로토타입 계획 **P0 착수 전**. 구현 코드는 아직 없고, 저장소도 아직 git으로 초기화하지 않았습니다.

**읽는 순서 (최소):**

1. `06_toolkit_spec.md` — §1 목적, §3 층, §5 공급 층, **§14 프로토타입 계획**, **§16 결정 현황**
2. `06a_findings_supply.md` — 공급 층과 프로토타입 우선의 근거

**작업 규칙:**

- 스키마를 먼저 설계하지 않습니다. P1~P3 실물에서 P4에 역산합니다.
- upstream 문장은 고치지 않습니다. 구조만 우리 규격으로 바꾸고, 불가피한 문장 변경은 `adapted`로 표시합니다 (06 §5.4).

**참고:** 설계 세션에서 만든 구조 다이어그램 페이지 [ko-quality 작동 구조](composition-structure.html)는 **05 기준**이라 06과 다릅니다. 유스케이스와 도입 전후 흐름을 볼 때만 참고합니다.

## 문서의 세 종류

한 단계는 최대 세 문서로 이루어지고, 번호를 공유해 짝으로 관리됩니다.

| 종류 | 파일 이름 | 시점 | 담는 것 |
|---|---|---|---|
| **단계 문서** | `NN_<이름>.md` | 그때 | 그 시점의 설계 결과물. 스펙 |
| **사이 문서** | `NNa_findings_<주제>.md` | 짓기 전 | 다음 단계로 넘어가며 알게 된 것, 바꾼 것, 되돌아볼 지점 |
| **실측 문서** | `NNb_built_<주제>.md` | 짓고 나서 | 구현해 보니 스펙과 달랐던 것, 스펙이 몰랐던 것 |

셋이 다 있어야 하는 것은 아닙니다. 단계 문서만 읽으면 결과가 보이고, 사이 문서를 같이 읽으면 왜 그 결과가 됐는지가 보이며, 실측 문서까지 읽으면 그 판단이 실제로 맞았는지가 보입니다.

**실측 문서를 쓰는 때.** 스펙대로 지었는데 다르게 동작했을 때, 스펙이 규정하지 않은 선택을 구현에서 해야 했을 때, 스펙의 수치나 임계값을 실측으로 바꿨을 때. 스펙을 고치는 것이 아니라 **차이를 기록하고**, 그 차이가 설계 자체를 바꿔야 할 만큼이면 다음 단계 문서를 엽니다.

첫 실측 문서는 `06b_built_prototype.md`이고, P0에서 만들어 프로토타입 단계마다 절을 덧붙입니다.

## 단계 요약

```text
01 아이디어      "Claude Code의 한국어가 깨진다. 비슷한 것들을 모아 최적 조합을 찾고 싶다"
   ↓ 조사        생태계는 생성 시점 개입 / 생성 후 개입으로 갈림. 평가를 해본 프로젝트는 하나뿐
02 스택          L0 policy ~ L4 eval 5층. 원칙: taxonomy 하나, LLM 판정과 결정론 판정 분리
   ↓ 재정의      재사용성 = 에이전트에게 기능으로 제공. 프롬프트 층은 텍스트+계약+회귀테스트여야 장치가 됨
03 엔진          MCP tools/resources/prompts = gate/taxonomy/지시문. 두 방향(생성 주입, 검토 위임)
   ↓ 결정        하네스 중립. 14개 결정. 되돌아볼 지점 3개
04 검증 엔진 안  gate·report·eval 로 LLM 층을 검증. 보류
   ↓ 전제 교체   근거를 되짚음 → 검증 비중은 사용자 관심사에서 온 것. upstream 신뢰 + 사용성 우선으로
05 구성 계층     upstream 을 profile·preset·agent 로 묶는 얇은 층 + 판정하지 않는 로거. 보류
   ↓ 선 교정     자른 기준이 검증/비검증이었음 → 판정/측정으로. 이 판단은 검증 단계로 이월
   ↓ 목표 재확인  산출물은 계측 장치가 아니라 쓸 수 있는 도구. 검증은 다음 단계
   ↓ 사양 조사    Claude Code·Codex 공식 문서 확인. 세 가지 제약 발견
06 툴킷          Skill 이 지시문, MCP 가 계산, 하네스별 렌더가 정책 주입. 구현 대상
   ↓ 구현 점검   그릇은 있고 내용물이 없음 → upstream 을 우리 규격으로 받는 공급 층. 추상화는 프로토타입 뒤
   ⋯ 프로토타입  P0 부터 (06 §14)
```

조사에서 나온 제약 셋이 06 의 형태를 결정했습니다.

- **출력 스타일은 서브에이전트에 닿지 않는다** → 정책을 에이전트 정의마다 직접 써넣는 것이 필수
- **Codex 의 MCP 는 tools 전용** → 지시문은 MCP prompt/resource 가 아니라 Skill 이 나른다
- **transcript 는 hook 의 안정적 입력이 아니다** → 로거는 hook 입력에서 점진적으로 조립한다

구현 점검에서 나온 원칙 둘이 06 의 진행 방식을 결정했습니다.

- **upstream 문장은 그들의 것, 형식은 우리의 것** → 문장은 고치지 않고 역할별 규격으로 정규화하며 출처를 단다
- **스키마는 실물에서 역산한다** → 세 벤더를 손으로 통과시킨 뒤 스키마를 만들고, 네 번째 벤더로 추상화를 시험한다

## 세 스펙의 관계

`04` → `05` → `06` 은 같은 대상의 세 판본이고, 셋 다 형식을 공유합니다. 구현 대상은 **06** 하나입니다.

| | 산출물 | 상태 |
|---|---|---|
| 04 | 검증 엔진. gate·report·eval 로 LLM 층을 검증 | 보류 — 목표 형태 |
| 05 | 구성 계층. 얇은 층 + 로거 | 보류 — 로거가 앞에 섰음 |
| **06** | **툴킷. 설치하면 쓰이는 도구** | **구현 대상** |

06 은 검증 단계의 부분집합입니다. profile·preset·agent·skill·레코드가 같은 형식을 쓰고, `ruleset`·`features`·`watch:`·`gate:`·eval 은 나중에 **더하는** 것입니다. 무엇을 어디에 더하는지는 06 §15에 있습니다. 검증 단계 문서의 번호는 열 때 정합니다.

## 04·05 시절의 관계 (참고)

05 는 04 의 부분집합입니다. profile·preset·agent 템플릿·로거 레코드는 같은 형식을 쓰고, 04 의 gate·report·eval 은 나중에 **더하는** 것입니다. 로거가 eval 케이스 형식으로 기록하고 층별로 policy off 를 섞어두므로, 검증이 필요해지는 시점에 재료가 이미 있습니다.

부분집합을 가르는 기준은 **판정하느냐 측정하느냐**입니다(05a). 판정은 값을 놓고 통과·중단을 정하는 것이고 04 에 있습니다. 측정은 값을 남기는 것이고 05 에 있습니다. 이 선을 처음에는 "검증이냐 아니냐"로 그었는데, 그 기준으로는 `ko.features` 처럼 판정하지 않는 측정 장치까지 04 로 넘어가 로거가 재는 값 없이 원문만 쌓게 됩니다.

두 스펙을 잇는 실제 장치는 profile 의 **`watch:`** 절입니다. 04 의 `gate:` 와 형식이 같지만 넘어도 막지 않고 레코드에 표시만 남깁니다. 그래서 gate 를 만들 때 threshold 를 추측하지 않고, 이미 실측으로 검증된 값의 **키 이름만 바꿉니다.** 전환은 한꺼번에 일어나지 않고 축 하나씩 승격됩니다.

## 개정 규칙

- **지난 단계 문서와 모든 사이 문서는 고치지 않습니다.** 그 시점의 기록이지 사양이 아닙니다. 나중에 틀린 것이 드러나면 전방 포인터나 상태 표시만 답니다 — `01_idea.md` 가 `02a` 를, `04a` 가 `05a` 를 가리키는 방식입니다.
- **현재 구현 대상인 단계 문서만 개정합니다.** 지금은 `06` 하나입니다. 개정 근거는 항상 사이 문서나 실측 문서에 있고, 단계 문서 머리말이 그것을 가리킵니다.
- **외부 사양에 기대는 절은 확인 날짜를 적습니다.** 하네스 사양은 빠르게 바뀝니다. `06 §2` 가 그 예이고, 착수 시 재확인 대상입니다.
- **실측 문서는 스펙을 고치지 않습니다.** 차이를 기록할 뿐이고, 스펙을 고칠지는 그 기록을 읽고 따로 정합니다.

## 저장소 안에서의 위치

```text
ko-quality/
├── design/          ← 이 디렉터리. 설계·판단·실측
├── upstream/        ← 그들의 것. 공급 층         (P0 부터)
├── assemble/        ← 우리의 것. 조립            (P1 부터)
├── build/  dist/    ← 만들어진 것               (P1 손으로, P5 부터 코드)
└── server/  logger/                            (P7)
```

전체 트리는 06 §4에 있습니다. 설계계획이 여럿이 되면 `design/<계획 이름>/` 으로 한 겹 내려 각 계획 안에서 번호를 새로 셉니다. 지금은 계획이 하나뿐이라 평평하게 둡니다.
