# 01. 아이디어: 저장소를 호스트 상태에서 떼어 내기

> 단계 문서. **끼어드는 시대**의 개념 문서다. 제품 설계를 여는 것이 아니라, 공개 기록과 호스트의 데이터를 어떻게 나누어 다룰지를 정한다.
> 입력은 2026-09-18의 이력 재작성 두 번에서 드러난 것과 `AGENTS.md`의 "Public repository" 절이다.

## 왜 이 시대가 있는가

공개 저장소의 기록은 누가 어느 기기에서 읽어도 같은 뜻이어야 한다. 이력을 재작성하면서 확인한 것은, 기록에 빌드한 기기와 계정의 상태가 섞여 들어가 있었다는 점이다. 이것은 개인 정보만의 문제가 아니다. 기록이 한 기기의 상태에 묶이면, 다른 사람이 같은 저장소로 같은 기록을 읽거나 재현할 수 없게 된다.

한편 호스트에 데이터를 쌓는 일 자체는 필요하다. 로거의 기록, 코퍼스, 빌드의 원시 자료가 모두 호스트에 쌓인다. 그러므로 이 시대가 원하는 것은 두 가지다.

1. 공개 기록에는 호스트 상태가 들어가지 않는다.
2. 호스트의 데이터는 로컬에서만, 정해진 규칙에 따라 관리된다.

## 이 시대가 생긴 경위: 이력 재작성 두 번 (2026-09-18)

- **1차 재작성.** 저장소 경로, scratch 경로, 사용자 범위 플러그인 이름, 사용자의 모델 설정을 지웠다. 해당 커밋부터 이력을 다시 썼고, 기록 안의 커밋 참조를 새 해시로 고치는 커밋을 마지막에 붙였다.
- **2차 재작성.** 1차가 놓친 것을 지웠다.
  - 시대 01 P6 기록에 남은 Codex 셸 경로와 scratch 경로
  - 하네스 세션 ID (P3, P6, P8·P9 코퍼스의 세션 목록)
  - 저장소 절대 경로에서 만든 `project` 해시 (P3)
  - 사용자 범위 플러그인과 마켓플레이스 이름 (E7)
  - 개인 Codex 설정에 있던 모델과 그 모델로 한 대조 실행
  - Codex 계정의 요금제와 사용 한도 (시대 01·02·99의 문서, README, 커밋 메시지)
  - 설계 기록에 걸려 있던 비공개 artifact 링크

  이번에는 첫 커밋부터 모든 커밋을 다시 만들었고, 과거의 모든 커밋 안에 있는 커밋 참조가 새 커밋을 가리키게 했다. 작성 날짜와 커밋 날짜는 원본을 그대로 보존했다. 1차의 참조 수정 커밋은 바꿀 내용이 없어져서 빠졌다. artifact는 HTML로 저장소에 들어갔다 ([`../../01-toolkit/3-spec/composition-structure.html`](../../01-toolkit/3-spec/composition-structure.html)).
- **지운 원래 값은 공개 기록에 남기지 않는다.** 원래 값은 빌드한 기기의 로컬 기록에만 있다.
- **재작성하면서 정한 기록 방식 (사용자, 2026-09-18).**
  - 하네스나 계정 때문에 측정하지 못한 것은 "측정하지 않음, 원인은 조사하지 않음"으로만 적는다.
  - 미룬 일은 날짜가 아니라 "미뤄 둠"으로 적는다. 시대 99도 이 방식으로 고쳤다.
  - 비용은 로그인 방식과 관계없이 토큰 수와 API 기준 환산 비용으로 적는다. 구독 계정으로 실행했더라도 API 사용자가 같은 기록을 읽기 때문이다.

## 드러난 것

1. **규칙이 좁다.** `AGENTS.md`는 개인 정보, 비밀, 기기별 경로만 금지한다. 재작성에는 그보다 넓은 기준(호스트 상태 전체)을 적용했지만, 그 기준과 목적은 어디에도 적혀 있지 않다.
2. **수작업 점검으로는 막지 못한다.** 서로 독립적으로 세 번 스캔했는데(빌더 한 번, 서브에이전트 두 번), 매번 다른 항목을 놓쳤다. 시대 01의 기록, 한국어로 적힌 요금제 표현, glob 패턴 안에 들어 있던 디렉터리 이름이 그 예다.
3. **발생원이 그대로 있다.** 코퍼스 생성기는 세션 ID를 커밋되는 요약 파일에 쓰고, Codex 실행 기록은 명령 문자열을 가공하지 않고 남긴다. 재작성은 결과만 지웠으므로, 다음 배치를 돌리면 같은 정보가 다시 들어온다.
4. **식별자가 호스트에 묶여 있다.** 로거의 `project`는 git 루트 절대 경로의 해시다 (시대 02 스펙 09 §12.1). 그래서 같은 저장소라도 clone한 위치가 다르면 다른 프로젝트로 집계된다.
5. **로컬 데이터가 흩어져 있다.** 로그 홈, 코퍼스 홈 세 개, 빌드 원시 자료, 재작성 백업이 서로 다른 곳에 있다. 보존 규칙(90일)은 `measure run`을 실행한 홈의 텍스트 디렉터리에만 적용된다. 세션 상태 파일(`state/`)은 보존 규칙 밖에 있어서, 세션 종료가 기록되지 않으면 프롬프트 원문과 함께 남는다. 로컬 기록(재작성 전 원문과 원시 자료의 위치)도 한 빌드의 scratch 안에 임시로 만들어져 있다.
6. **비용 기록이 로그인 방식에 묶여 있었다.** Codex는 비용을 보고하지 않으므로, P2 기록에는 비용이 0으로 적혀 있었다.

## 원하는 것

| # | 무엇 | 내용 |
|---|---|---|
| A | 공개 기록 규칙 | 목적, 금지 범주, 로컬 자료를 가리키는 방식(경로가 아니라 `<scratch>`, `<local>` 같은 역할 이름), 측정하지 못한 것과 미룬 일과 비용을 기록하는 방식. `AGENTS.md`에 둔다 |
| B | 로컬 데이터 규약 | 로컬 루트 하나와 시대별 구조, 로컬 기록의 위치와 형식, 원시 자료와 `state/`까지 포함하는 보존 규칙, 정리 절차 |
| C | 기계적 차단 | 빌드 검사 check 7과 pre-commit hook. 추적되는 파일과 커밋 메시지를 모두 검사한다. 금지 목록은 검사하는 시점에 호스트에서 만든다(사용자 이름, 홈 경로, 저장소 절대 경로와 그 해시, 설치된 사용자 범위 플러그인, scratch 경로 형태). 여기에 고정 패턴(UUID 형태, 요금제와 사용 한도 어휘, 한국어 표현 포함)을 더한다 |
| D | 발생원 차단 | 코퍼스 생성기는 커밋되는 요약에 `key`만 쓰고, `key`와 세션 ID의 대응은 로컬 진행 파일에만 둔다. 명령 문자열은 커밋하기 전에 가린다. Codex 비용은 토큰 수에 가격표(출처와 날짜 포함)를 곱해 환산한다 |
| E | `project` 식별자 | 절대 경로 대신 저장소에 내재한 값으로 바꾼다. 이미 쌓인 로컬 로그의 값을 어떻게 다룰지 정한다 |

## 다른 시대와의 관계

- **시대 02.** `7-review` 전에 멈춰 있다. 멈춘 지점은 태그 `era02-6build-end`다. 이 시대가 `dev`에 머지된 뒤 재개하며, 재개한 리뷰는 태그 시점의 빌드를 대상으로 하고 리뷰 문서는 이 시대의 규칙을 따른다.
- **시대 02의 스펙.** 이 시대는 09를 고치지 않는다. 이 시대의 스펙이 09의 해당 절(§12.1 `project`, §13 빌드 검사, §18 코퍼스 요약)을 대체한다고 적고, 09에는 전방 포인터만 단다.
- **시대 03.** 시대 02의 리뷰 결과와 이 시대의 결과를 함께 받는다.
- **`master`.** `master`는 리뷰를 거친 안정된 변경만 받는다(사용자, 2026-09-18). 이 시대의 머지도 리뷰에서 정한다.

## 순서에 대한 초기 생각

C를 가장 먼저 짓는다. 그러면 시대 02의 리뷰 문서를 포함해 이후의 모든 커밋이 바로 보호받는다. A와 B는 C가 쓰는 금지 범주와 같은 정의를 쓴다. D는 시대 03이 다음 배치를 돌리기 전에 끝나야 하고, E는 로그의 의미를 바꾸므로 역시 시대 03 전에 끝나야 한다.

## 열린 질문

- **금지 범주의 경계는 어디인가.** 저장소 자신의 공개 정체성(GitHub 계정과 저장소 이름, LICENSE의 저작권자)과 시험 조건으로 적은 도구 버전은 허용한다. 그 사이에 있는 것, 예를 들어 개인 설정에서 온 모델 이름이 시험 조건이 되는 경우는 어떻게 가를 것인가.
- **호스트에서 만든 금지 목록은 무엇을 보장하는가.** 목록이 기기마다 달라지므로, 다른 기여자의 기기나 CI에서 검사가 통과했다는 것은 그 기기의 정보가 없다는 뜻일 뿐이다.
- **pre-commit hook을 설정하지 않은 clone은 어떻게 다룰 것인가.** hook은 clone마다 설정해야 한다(`core.hooksPath`).
- **check 7은 과거 이력까지 볼 것인가, 새 커밋만 볼 것인가.**
- **`project`에 무엇을 쓸 것인가.** 첫 커밋 해시는 이번처럼 이력을 재작성하면 바뀐다. 무엇이 더 안정적인가.
- **로컬 데이터는 언제 지우는가.** 빌드 원시 자료는 리뷰가 끝날 때까지 필요하다. 시대 단위로 지울 것인가, 기간으로 지울 것인가. 재작성 백업은 언제 지울 것인가.
