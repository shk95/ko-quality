# 06a. 공급 층: upstream을 우리 규격으로 받는다

> 사이 문서. 06 툴킷 스펙을 "구현 가능한가"로 되짚으면서 알게 된 것. upstream과 우리 사이에 공급 층을 끼우고, 추상화는 프로토타입 뒤로 미룬다.

## 06을 구현 가능성으로 되짚음

06은 하네스 사양을 실제로 조사해 제약 셋(출력 스타일이 서브에이전트에 안 닿음, Codex MCP가 tools 전용, transcript 불안정)을 착수 전에 확보했다. 이건 보통 구현 중반에 발견되어 재작업을 부르는 종류라 실제로 시간을 아낀 부분이다.

그러나 S0~S1 너머로는 구현할 수 없었다.

**그릇은 있고 내용물이 없었다.** 431줄 중 스킬의 실제 지시문 텍스트에 관한 것이 없었다. §7은 "`ko-rewrite` = im-not-ai 절차"라고 이름만 적었는데, 모델의 행동을 바꾸는 것은 절차의 이름이 아니라 문장이다. 04를 두고 "해상도가 필요 이상으로 높았다"고 한 비판이 06에도 같은 모양으로 적용된다 — 구조는 촘촘하고 모델이 읽을 문장은 없다.

**세 절이 서로 어긋났다.**

- §5: upstream을 수정하지 않는다
- §7: `skills/ko-rewrite/SKILL.md`가 im-not-ai 절차를 담는다
- §12: `dist/`에 `vendor/`가 들어가지 않는다

vendor가 배포되지 않으면 스킬이 텍스트를 직접 들어야 하고, 그러면 `vendor/`와 `skills/`에 같은 내용이 두 벌 생긴다. upstream 커밋을 올릴 때 손으로 옮겨야 하고, "수정하지 않는다"가 지켜지는지 확인할 방법이 없다.

**결정되지 않은 셋.**

1. upstream 텍스트를 복사할 것인가, 동봉할 것인가, 사용자가 따로 설치하게 할 것인가
2. 프로파일은 런타임에 모델이 읽는가, 빌드타임에 렌더되는가
3. 정책 합성 규칙 — 블록 위치, `keep-coding-instructions`, 원본 frontmatter, Codex 32 KiB 대비

## 제안: 공급 층

의존하는 upstream의 버전을 고정하고 합의된 인터페이스를 공급하는 영역을 따로 둔다. 원본을 dump로 쌓지 않고, 우리 규격으로 정규화해 둔다.

```text
upstream 원본 (커밋 고정, 받아오기만 함)
   ↓ 추출기 — 벤더마다 하나
정규화 산출물 (역할별 규격, 커밋됨)
   ↓ 하류는 이것만 읽는다
skills · agents · output-styles → dist/
```

**왜 맞는가.**

- **"수정하지 않는다"가 검사 가능해진다.** 원본은 커밋과 바이트가 같고, 변환은 코드로 결정적이고, 산출물은 출처를 단다.
- **upstream을 올리면 변화가 우리 말로 보인다.** 정규화 산출물의 diff가 곧 변경 내역이다. 지금은 커밋을 올려도 동작이 바뀌기 전까지 무엇이 바뀌었는지 모른다.
- **upstream이 구조를 바꾸면 빌드가 크게 실패한다.** 조용히 드리프트하지 않는다. 03a가 `category_map`을 두고 "upstream 하나가 분류를 바꾸면 이 파일만 고친다"고 한 원칙이 전체로 일반화된다.

## 조건 1 — 구조는 바꿔도 되고 문장은 바꾸지 않는다

06의 전제는 upstream을 신뢰한다는 것이다. 추출하면서 문장을 다듬으면 신뢰 대상이 upstream 작성자가 실제로 써서 굴려본 텍스트에서 **우리가 고쳐 쓴, 아무도 검증하지 않은 텍스트**로 소리 없이 교체된다.

그래서 변환을 세 등급으로 나누고 기본값을 가장 엄격하게 둔다.

| 등급 | 허용 | 예 |
|---|---|---|
| `verbatim` | 문장 그대로, 위치만 옮김 | 절차 단계를 `steps[]`로 |
| `selected` | 부분만 고름 | im-not-ai에서 Claude Code 다중 에이전트 구성 부분을 뺌 (03a #3) |
| `adapted` | 문장을 바꿈. **불가피할 때만** | "finalizer 에이전트가 ~한다" → "~한다" |

`adapted`는 원문을 옆에 남기고 개수를 센다. 그 숫자가 우리가 upstream에서 얼마나 멀어졌는가의 지표다. 효과를 재는 단계에서 이 구간이 먼저 의심 대상이 된다.

## 조건 2 — 인터페이스는 벤더가 아니라 역할 단위

하류가 "im-not-ai"를 요청하지 않고 "rewrite 절차"를 요청한다. upstream을 갈아끼워도 하류가 안 바뀐다.

| 역할 | 담는 것 | 현재 공급자 |
|---|---|---|
| `policy` | 본문, 변형(coding / not-coding), 선택 블록, 원본 frontmatter | fluent-korean |
| `procedure` | 단계, invariant, 입출력 계약, 참조 | im-not-ai(rewrite), korean-skills(grammar), yoonmoon(diagnose) |
| `taxonomy` | 범주, 패턴, 심각도 | im-not-ai(rewrite), yoonmoon(diagnose) |
| (검증 단계) `ruleset` | 결정론 규칙 | 미정 |

- **형식을 맞추는 것이지 내용을 합치는 게 아니다.** rewrite taxonomy와 diagnose taxonomy는 같은 형식을 쓰되 별개 슬롯이고, 한 컨텍스트에 둘을 올리지 않는다는 02a 이후 원칙은 그대로다.
- **`procedure`·`taxonomy` 슬롯에는 공급자가 하나다.** 02의 "rewrite taxonomy는 하나만"이 구조로 강제된다.
- **`policy`는 조각 합성이 가능하다.** 02가 fluent-korean과 stop-slop-ko 규칙을 함께 얹으려 한 것처럼, 정책은 여러 공급자의 조각을 합칠 수 있다. 조각마다 출처를 단다.

## 출처 기록

모든 조각에 붙는다.

```yaml
provenance:
  upstream: im-not-ai
  commit: <sha>
  path: <upstream 안의 파일>
  anchor: "<제목 텍스트>"
  content_hash: sha256:<조각 해시>
  transform: verbatim | selected | adapted
```

줄 번호는 upstream이 재포맷하면 깨지므로 기준으로 쓰지 않는다. **앵커로 찾고 해시로 확인한다.** 재추출 때 앵커를 못 찾거나 해시가 달라지면 빌드가 멈춘다. 라이선스 고지도 이 기록으로 충족된다.

## 원본을 커밋하지 않는다

원본은 lock으로 받아오고 캐시에만 두며, 정규화 산출물만 커밋한다. 저장소가 담는 upstream 내용은 전부 우리 규격이다.

대가는 하나다. upstream 저장소가 사라지면 재추출을 못 한다. 정규화 산출물이 커밋돼 있으므로 도구는 계속 동작하고, 필요하면 원본 tarball을 캐시로만 보관한다.

## 공급 층으로 보니 드러난 것

06을 "누구의 문장인가"로 다시 읽자 세 곳이 걸렸다.

**① 06 §7의 invariant에 우리 문장이 섞여 있었다.** `ko-rewrite` invariant 목록의 "신호가 둘 이상 겹칠 때만 수정"은 im-not-ai가 아니라 hjongc/humanizer-kr의 원칙이고, 03a #3이 우리 판단으로 더한 것이다. 06에서는 이것이 im-not-ai 절차와 같은 목록에 구분 없이 들어가 있었다.

`procedure` 슬롯은 공급자가 하나이므로 hjongc를 두 번째 공급자로 넣을 수 없다. **우리 문장으로 분류해 조립 쪽 템플릿에 두고 출처 주석을 단다.** 공급 층이 없었다면 이 구분은 계속 보이지 않았을 것이다.

**② `policy-blocks/`는 우리 것이 아니었다.** 05 §3이 "fluent-korean README의 선택 블록만"이라고 적었듯 `subagent-propagation`, `honorific`, `think-in-korean`은 fluent-korean의 문장이다. 06은 이것을 우리 자산처럼 최상위에 두었다. **정규화된 `policy`의 선택 블록으로 옮기고, 조립 쪽은 프로파일별로 어느 블록을 켤지만 고른다.**

**③ `exempt`가 존재하지 않는 규칙을 가리켰다.** formal-report의 `exempt: [slop.cta_in_sns, slop.polite_email_ending]`는 stop-slop-ko의 규칙 id인데, 06의 공급자 목록에 stop-slop-ko가 없다. 참조 대상이 없는 설정이다. **stop-slop-ko를 `policy` 조각 공급자로 넣을지 결정할 때까지 `exempt`를 비운다.**

## 세 결정에 미치는 영향

| 결정 | 영향 |
|---|---|
| ① 복사 / 동봉 / 참조 | **해소.** 네 번째 안 — 결정적 추출 + 출처 기록 + 정규화 산출물 커밋 |
| ② 프로파일 런타임 / 빌드타임 | **빌드타임 쪽으로 기운다.** 정규화 → 조립 → 렌더 파이프라인이 이미 있으므로 프로파일별 렌더가 자연스럽다. 프로토타입에서 확정 |
| ③ 정책 합성 규칙 | **한곳에서 정해진다.** 정규화된 `policy` + 선택 블록의 함수가 되므로 조립 단계 하나에서만 결정한다. 프로토타입에서 확정 |

## 경계할 것 — 그릇을 한 겹 더 그리는 일

06을 "그릇만 그렸다"고 평가해놓고 공급 층을 추상 스키마부터 설계하면 같은 실수를 반복한다. 공급 층은 그릇을 한 겹 더 두는 일이기 때문이다.

그래서 **순서를 뒤집는다.**

1. 스키마 없이, 한 벤더를 손으로 정규화하고 거기서 스킬 하나를 렌더해 실제 하네스에서 돌린다
2. 같은 역할의 두 번째 벤더, 성격이 다른 역할의 세 번째 벤더로 넓힌다
3. 세 실물에서 스키마를 역산한다
4. **네 번째 벤더를 스키마만 보고 넣는다.** 스키마를 고치지 않고 들어가면 추상화가 성공한 것이다

4번이 추상화의 성공 기준이다. 스키마가 세 실물을 설명하는 것은 당연하고, 보지 않은 네 번째를 받아낼 때만 추상화라고 부를 수 있다.

## 되돌아볼 지점

| 항목 | trade-off | 지금의 선택 |
|---|---|---|
| 문장 변환 금지 기본 | `adapted`가 불가피한 곳이 많으면 등급 체계가 번거로워진다 | 첫 벤더에서 실제 개수를 본다. 많으면 upstream 선택 자체를 다시 본다 |
| 원본 미커밋 | upstream이 사라지면 재추출 불가 | 정규화 산출물로 도구는 유지. 필요 시 tarball 캐시 |
| 앵커 + 해시 | upstream 제목이 자주 바뀌면 빌드가 자주 멈춘다 | 멈추는 쪽을 택한다. 조용한 드리프트보다 낫다 |
| 스키마 후행 | 프로토타입 동안 형식이 흔들린다 | 흔들림 자체가 추상화 재료. 실측 문서에 기록한다 |
| hjongc 원칙을 우리 문장으로 | upstream 신뢰 범위 밖의 텍스트가 스킬에 들어간다 | 출처 주석과 함께 조립 템플릿에 분리해 두어 식별 가능하게 한다 |
